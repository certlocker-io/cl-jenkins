# Using Trust secrets in Pipeline

[Installation and configuration](configuration.md) · [Plugin overview](../README.md)

## Recipes for every secret type

| Stored secret | Binding options | What the variable contains |
| --- | --- | --- |
| PASSWORD / stored API token | defaults | Exact text value |
| CREDENTIALS username | `field: 'username'` | Username text |
| CREDENTIALS password | `field: 'password'` | Password text |
| PEM / PRIVATE_KEY generated by Trust | `field: 'key', mode: 'FILE'` | Path to the actual key material |
| PEM associated username | `field: 'username'` | Username text, if present |
| CONFIGURATION, complete file | `mode: 'FILE'` | Path to unchanged contents |
| JSON configuration value | `field: '/database/password'` | Selected nested scalar |
| Certificate PEM stored as plain text | `mode: 'FILE'` | Path to unchanged PEM contents |
| Any structured secret, complete JSON | `mode: 'FILE'` without `field` | Path to complete fetched JSON |
| Base64-encoded binary keystore/DER | `mode: 'FILE', base64: true` | Path to decoded binary bytes |

Trust-generated PEMs and private keys are JSON objects containing a `key` property.
Select that property when a tool needs the actual key file. There is no automatic conversion
between key formats or algorithms: RSA, EC, Ed25519 and other returned contents are preserved.

Bind both halves of credentials; one request fetches the shared secret:

```groovy
node {
    withCertLockerSecrets(server: 'production', secrets: [
        [secretId: 'database-credentials-id', field: 'username', variable: 'DB_USER'],
        [secretId: 'database-credentials-id', field: 'password', variable: 'DB_PASSWORD']
    ]) {
        sh './database-migrate.sh'
    }
}
```

Use private files inside a `node`/Declarative agent block:

```groovy
node {
    withCertLockerSecrets(server: 'production', secrets: [
        [secretId: 'configuration-id', variable: 'APP_CONFIG',
         mode: 'FILE', fileName: 'application.yaml'],
        [secretId: 'keystore-id', variable: 'CLIENT_KEYSTORE',
         mode: 'FILE', base64: true, fileName: 'client.p12']
    ]) {
        sh './start-client.sh' // reads APP_CONFIG and CLIENT_KEYSTORE paths
    }
}
```

ENV-only bindings can run without allocating an agent. An empty ENV value removes that
variable within the block, following Jenkins environment semantics; use FILE to preserve an
empty file. They can also be used inside a
Declarative `steps` block. Both steps appear in Jenkins' **Pipeline Syntax → Snippet Generator**;
server and binding-mode choices are available in its forms.

## Binding options

`withCertLockerSecrets(server, secrets)` accepts optional `account`. Each binding accepts:

| Option | Default | Meaning |
| --- | --- | --- |
| `secretId` | required | Trust secret ID |
| `variable` | required | Environment variable receiving the value or file path |
| `mode` | `ENV` | `ENV` for UTF-8 text, `FILE` for a private temporary file |
| `field` | unset | Complete contents, a top-level JSON field, or RFC 6901 pointer |
| `fileName` | `secret` | Plain filename inside a private per-binding directory |
| `base64` | `false` | Decode Base64 after field selection |

A JSON pointer begins with `/`; escape `/` in property names as `~1`, and `~` as `~0`.
Arrays inside objects support numeric pointer components. Selected fields must exist and
be non-null scalar values; strings, numbers and booleans are supported. Missing values or
invalid Base64 fail the step. Complete raw contents are never trimmed or reserialized.

Variables must be unique and valid environment names. Execution-sensitive names such as
PATH, HOME, SHELL, LD_PRELOAD, LD_LIBRARY_PATH, JAVA_TOOL_OPTIONS, JDK_JAVA_OPTIONS,
TRUST_API_TOKEN and TRUST_URL are reserved. Limits are 32 bindings, 4 MiB per fetched secret,
16 MiB total fetched data per block, and 64 KiB per ENV value. Binary/NUL-containing values
require FILE mode. Fetches are cached only within one block, by secret ID; nothing is
cached between builds or blocks, so a later block can see a rotated secret.


## Direct Trust API access

For operations beyond fetching secrets, the existing `withCertLockerOIDC` step remains
available. It exposes the short-lived Trust access token and base URL for the block:

```groovy
node {
    withCertLockerOIDC(server: 'production', tokenType: 'SECRET') {
        sh './trust-api-operation.sh' // reads TRUST_API_TOKEN and TRUST_URL
    }
}
```

`tokenType` also supports `CERTIFICATE` and `MCP` if permitted by the Trust principal.
These are Trust access-token categories, distinct from API tokens stored as secret values.
Use the HTTP `x-api-token` header for direct API calls. Use single-quoted Groovy shell scripts
and let the shell expand variables, instead of putting secret values in Groovy arguments.
The OIDC block masks its access token; secret values fetched by custom scripts need their
own handling. Prefer `withCertLockerSecrets` for automatic retrieval and masking.

## Security, cleanup and lifetime

- HTTPS certificates and hostnames are validated against the controller JVM trust store.
  Install private CAs there as needed. No TLS bypass or redirect following is provided.
- Requests have connection/read timeouts. Errors omit tokens and response bodies. Secret
  fetches use `/rest/api/v1/secret/{account}/fetch/{id}`, preserving Gateway authorization,
  audit and step-up behavior. A failed fetch prevents the body from running.
- Values and their non-empty lines are masked in console output within the block and marked
  sensitive for Pipeline. Persisted bindings and masking patterns use encrypted Jenkins
  `Secret` values. Masking is best-effort: encoding, transforming or deliberately disclosing
  a value can defeat it. Arbitrary binary file output has no reliable text masking.
- FILE bindings are written on the selected agent, in random system temporary directories
  outside browsable workspaces, even inside `dir(...)`. On Unix directories are 0700 and
  files 0600. Windows protection depends on agent account/TEMP ACLs. Use isolated agents.
- Environment variables are restored and temporary files deleted after success, body failure
  or normal cancellation. Controller restart/resumption keeps the binding. If the agent is
  lost permanently, or Jenkins is killed during setup before its cleanup callback is saved,
  cleanup cannot be guaranteed; remove stranded `certlocker-secrets-*` directories from that
  agent's TEMP as part of its operational cleanup. The plugin never archives secret files.
- Trusted build authors and agent processes can access their bound values. Keep Trust
  principal permissions narrow. Do not copy secret files into artifacts or the workspace.
- No automatic token refresh, revocation on block exit, or secret write/rotation is performed.
  Issued API tokens remain valid until their server-controlled expiry. Keep API blocks within
  the token lifetime; open a new block to obtain a fresh token later. A retry during issuance
  can create another short-lived token; issuance is not exactly-once.
- This release supports Pipeline. It does not add a Freestyle build wrapper or Jenkins
  Credentials Provider synchronization, and it never copies Trust secrets into Jenkins'
  permanent credentials store.
